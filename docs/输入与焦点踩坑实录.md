# 世界终端屏：输入与焦点踩坑实录（2026-09-05/06）

> 本文记录"世界面片终端"从**完全不可交互**到**全键可用的完整排障过程**：
> 五个连环 bug、每个的真因与证据链、定位方法论，以及沉淀出的架构原则。
> 配套代码：`UShellWorldScreen`（宿主）、`SShellTerminalPanel/UShellSubsystem`（插件 Shell_UE）。
> 键归属契约速查见《宿主接入指南》§6.6。

## 0. 五坑速查表

| # | 症状 | 真因（一句话） | 修复锚点 |
| --- | --- | --- | --- |
| 1 | 世界屏点击/悬停毫无反应 | `Screen` 设了 `NoCollision`，对交互组件的 Visibility 物理射线"隐形" | QueryOnly + 仅挡 Visibility |

| 5 | InputWindow 态 Tab/ESC 失效（ESC 修好 Tab 仍死） | PIE 内未处理键被**编辑器全局命令兜底层**截胡（Tab 恰是编辑器绑定键） | 面板捕获 + `OnHostFlowKey` 委托归还宿主 |

## 1. 坑一：`NoCollision` 让世界屏对交互射线隐形

### 现象
世界面片终端无法点击、无法悬停、无法滚动——交互组件像不存在一样。

### 排查弯路
最初怀疑"没有转发链路"（这确实是次因：菜单场景 Pawn 无输入绑定，
`Click()/ScrollWheel()` 是零调用者的死代码），补上转发链后依然无效。

### 真因
读引擎源码 `UWidgetInteractionComponent::PerformTrace()`：
交互组件命中 widget 面片用的是 **Visibility 通道的物理射线**
（`LineTraceMultiByChannel`），并显式跳过不可见（`IsVisible()`）的
widget 组件。而 `Screen` 被设了 `NoCollision` —— **射线直接穿透，
屏幕对交互系统完全隐形**。hover、click 一切交互的地基就此塌掉。

另有一个容易踩的隐藏行为：交互组件自动忽略**同 Actor/附件根下**的
所有非 WidgetComponent 兄弟件（`GetRelatedComponentsToIgnoreInAutomaticHitTesting`），
所以代理面片不会挡射线——这是引擎的贴心设计，但别指望它替你把碰撞打开。

### 修复
```cpp
ScreenComponent->SetCollisionEnabled(ECollisionEnabled::QueryOnly);
ScreenComponent->SetCollisionResponseToAllChannels(ECR_Ignore);
ScreenComponent->SetCollisionResponseToChannel(ECC_Visibility, ECR_Block);
```
QueryOnly + 仅挡 Visibility：游戏碰撞、物理、重叠事件全部不受影响。

### 原则
**WidgetComponent 的"可交互性" = 渲染可见 + 碰撞对 Visibility 可命中，两者缺一不可。**
`NoCollision` 的 widget 面片在引擎交互系统眼里等价于不存在。

### 验证技巧
`InteractionComponent->GetHoveredWidgetComponent()` 是完美的程序化 hover
探针：配合 `InteractionSource=World` + 摆位（组件放到屏幕后方、朝向面板），
不碰物理鼠标即可断言"射线能否命中面片"。

## 2. 坑二：Slate 焦点是 per-user 的——"看着聚焦了"却打不了字

### 现象
点击世界屏后，输入框光标明明在闪，键盘敲下去却没有任何字符到达终端。

### 真因（两个机制叠加，均经引擎源码逐行确认）
1. **虚拟点击只作用于虚拟用户**：`UWidgetInteractionComponent` 注入的
   指针事件用 `VirtualUser->GetUserIndex()` 构造（WidgetInteractionComponent.cpp）。
   `SEditableText` 收到后 `Reply.SetUserFocus(...)` —— 焦点设置给
   **虚拟用户**，光标因此显示；但物理键盘路由沿**键盘用户**的焦点路径，
   与虚拟用户互不相通。
2. **物理点击的"焦点跟随"夺走键盘焦点**：世界面片是 3D 的，真实光标
   下方没有任何屏幕空间 widget，Slate 只看到游戏视口；而
   `SViewport::SupportsKeyboardFocus()` 返回 `true`（SViewport.h），
   于是 Slate 的 focus-follows-click 把**键盘用户**的焦点移到视口
   （SlateApplication.cpp 尾部的 SetUserFocus 循环）——打字通道被切断。

### 修复
点击**确实落在本屏**时（`IsPointerOverSelf()` 门槛，见 §7 多屏仲裁），
调用 `FocusTerminal()` 重新断言**键盘用户**焦点——`SetKeyboardFocus`
内部即 `SetUserFocus(GetUserIndexForKeyboard(), ...)`。这就是真实 UI
"点击文本框获得焦点"的世界屏等价物。

### 原则
- **Slate 一切焦点 API 都是 per-user 的**：混合"虚拟注入"与"物理键鼠"
  时，必须显式管理**键盘用户**的焦点；
- 世界 3D 面片上的点击天然"没有屏幕空间落点"，焦点断言必须由宿主主动补。

## 3. 坑三：修复"成功"了，但你测的是旧 DLL（热重载命名陷阱）

### 现象
焦点断言修复构建"成功"后，用户实测 Ctrl+C 依旧失效——且和打字失效
（同一焦点路径）一起出现。逐项排除引擎机制（`SEditableText` 的
`ClearKeyboardFocusOnCommit`？插件已显式 `false`；`UUserWidget` 吞
preview 事件？默认 Unhandled……）全部无果。

### 真因（在交付链路，不在代码）
检查 `Binaries/Win64` 发现：

```
UnrealEditor-UE_Shell_Project.dll        20:24   ← 编辑器实际加载的基础名 DLL
UnrealEditor-UE_Shell_Project-0002.dll   20:40   ← 焦点修复写进了这里
UnrealEditor-UE_Shell_Project-0003.dll   21:06   ← 后续修复写进了这里
```

UBT 检测到**任意 UnrealEditor 进程在运行**（哪怕属于另一个项目）就走
热重载命名模式，把产物写成 `-000X.dll` 变体；而**新启动的编辑器会话只
加载基础名 DLL**。用户测的一直是修复前的 20:24 旧代码。

### 修复（流程性）
1. 停编辑器并确认进程完全退出（`tasklist` 核对）；
2. 删 `Intermediate/Build/.../HotReloadState.json`、`Metadata-HotReload.json`、
   `Makefile.bin` 及所有 `-000X`/`patch_0` 残留；
3. 临时 `Saved/UnrealBuildTool/BuildConfiguration.xml`：
   `<UEBuildConfiguration><bAllowHotReloadFromIDE>false</...>` —— 精确
   跳过热重载命名判定（注意节点名是 `UEBuildConfiguration`，写
   `BuildConfiguration` 会被 XML schema 拒绝）；构建后**还原**该文件；
4. 构建后核对：产物必须是 canonical 名且时间戳更新。

### 原则
**"构建成功" ≠ "修复生效"。** 编辑器在跑时 UBT 的产物不落到加载器
实际读取的文件；每次改完 C++，必须核对 Binaries 下 DLL 的命名与时间戳。
跨项目的编辑器进程也会触发此行为（互斥锁与命名判定都按引擎 exe 级别，
不分项目）。

### 顺带的健壮性加固（排查中发现的真缺陷）
- `UWidgetInteractionComponent::ModifierKeys` 是 **protected 快照成员且
  永不自动更新**——不主动同步，注入的指针事件永远不带 Shift/Ctrl/Alt
  （Shift+拖选文本、Ctrl+点击全部失效）。薄子类
  `UShellWidgetInteractionComponent::SyncModifierKeys()` 在每次注入前
  从 `FSlateApplication::Get().GetModifierKeys()` 同步；
- `SetInputActive(true)` 在 PlayerController 未就绪时按帧重试（封顶
  60 次并告警），消除"标志为 true 但绑定不存在"的静默输入死区；
- `IsPointerOverSelf()`：多屏共存时 hover 命中**本屏**才转发/聚焦，
  防止双份事件注入与跨屏抢焦点。

## 4. 坑四：命令层不该决定呈现——裸 `login` 唤出全屏面板

### 现象
世界屏输入 `login` 回车，凭空弹出一个全屏 HUD 终端。

### 真因
`UShellSubsystem::Prompt()`（插件）的原实现：**无论当前有没有终端
表面，都 CreateWidget 一个全屏 HUD、AddToViewport、并切 UIOnly 输入
模式**。裸 `login` 走交互式提示（username/password），正好触发。
这是插件早期"提示符必须有一个全屏表面"的假设，与世界面片呈现冲突。

### 修复：命令层发状态，表面层订阅
与终端**输出**机制完全同构——输出早就走 `OnShellOutput` 广播（多实例
等价渲染），唯独 prompt 状态被单例直设。补齐同款接缝：

- 新增 `OnPromptChanged(bActive, Label, bMasked)` 广播 +
  `GetPromptLabel()/IsPromptMasked()` 查询；
- `Prompt()`：更新状态 → **有打开的全屏表面才**直设它（全屏范式旧行为
  保留）→ 广播；**无表面时不创建任何 UI、不碰输入模式**；
- `CloseTerminal()` 仅在曾有打开的全屏表面时才切回游戏输入模式
  （`quit`/`menu`/login 成功路径不再越权改写宿主输入状态）；
- `UShellTerminalWidget` 订阅广播转发自己的面板——世界屏实例与全屏
  实例独立呈现；`Open()` 时按子系统当前状态补同步（提示流中途打开
  不丢状态，密码掩码正常）。

### 原则
**命令逻辑层永远不决定呈现表面**（创建/打开/输入模式）。表面
（全屏 HUD、世界面片、未来的手柄 UI）是等价的订阅者。判定标准：
命令代码里出现 `CreateWidget`/`AddToViewport`/`SetInputMode` 任何
一个，就是越权。

## 5. 坑五：PIE-in-editor 的编辑器全局兜底吃掉了 Tab

### 现象
流控键所有权模型（`FlowKeyMode=HostOwned`：面板对 Tab/ESC 透传）落地后，
**ESC 有用了，Tab 依然死**。

### 定位过程（方法论示例：程序化二分）
1. **插桩**：PC 加临时 `DebugSimulateTab()`——构造与物理按键等价的
   `FKeyEvent` 直接调 `FSlateApplication::ProcessKeyDownEvent`（走完整
   真实链路），并打印 `GetKeyboardFocusedWidget()->GetTypeAsString()`
   与最终 `handled` 值；面板透传分支打印日志。
2. **数据**：焦点 = `SEditableText` ✓；面板透传日志 ✓；**handled=1**
   且游戏动作未触发 → 消费者在面板**下游**。
3. **排除法**：`SEditableText::HandleKeyDown` 的 Tab 分支要求
   `CanTypeCharacter('\t')`（默认 false，插件未绑 `OnIsTypedCharValid`）；
   `FNavigationConfig` 不在 `ProcessKeyDownEvent` 内消费；游戏侧唯一的
   InputPreProcessor（InputDeviceSubsystem）不消费按键；`SVirtualWindow
   : SWindow` 无键处理。
4. **锁定**：冒泡终点无人处理后，未处理键落入
   **`FSlateApplication::UnhandledKeyDownEventHandler`** —— 全源码树
   唯一绑定者是**编辑器主框架**（`MainFrameActions.cpp:97`）：
   `FMainFrameCommands::ActionList->ProcessCommandBindings(InKeyEvent)`。
   **Tab 恰是编辑器绑定键**（UI 焦点导航）→ 被吃；ESC 无绑定 → 放行。
   与全部实验数据自洽。

### 为什么透传方案本身不健壮
独立打包运行游戏没有编辑器兜底层，Tab 会正常到达游戏输入——**同一份
代码在 PIE 内和独立运行行为不一致**。行为随环境漂移即架构缺陷。

### 修复：面板捕获 + 委托归还宿主
`HostOwned` 语义重定义：面板对 Tab/ESC **既不透传也不自持**，而是

```
面板捕获（return Handled）→ UShellSubsystem::OnHostFlowKey(KeyName) 委托
→ 宿主订阅：Tab→HandleTerminalToggle()，ESC→HandleEscapeUI()
```

- 键**不依赖游戏输入管道**，PIE 内外、打包后行为完全一致；
- **无订阅者时安全忽略**——插件仍不假设任何默认行为；
- **双管道互补且单次触发**：面板持有焦点（InputWindow 态）走委托管道；
  无焦点（Shrink/HeldInHand）走 IMC_Shell 游戏输入管道。同一宿主语义
  函数覆盖两种场景。

### 原则
- **键监听点选在"焦点必然经过"的层，语义通过委托归还所有者**；
- **跨环境一致性（PIE 内 vs 独立运行）是健壮性的硬标准**——凡"只在
  某种环境下正常"的方案都藏着未显式化的依赖；
- PIE-in-editor 的键盘链有编辑器全局兜底，且**焦点在虚拟窗口
  （SVirtualWindow）时冒泡链不含 SViewport**——游戏输入的可达性
  与直觉不同，必须实测。

## 5b. 坑六："提示语是契约"——虚假广告制造的伪 bug

### 现象
登录界面按 ESC 没反应，且"似乎经常出现"。之前的修复只覆盖了
Gameplay 场景的 ESC 语义。

### 真因（两层叠加，但都成立）
1. **行为层（其实是正确的）**：HostOwned 迁移后，ESC 所有权归宿主；
   PC 的 `HandleEscapeUI` 只在 Gameplay 的 InputWindow 态有动作，
   菜单场景**故意空操作**（世界屏即登录 UI 本体，没有可退出的输入态；
   Shell 常规约定清行归 Ctrl+C）。键到达了、语义就是不动作。
2. **呈现层（真正的缺陷）**：面板状态栏硬编码
   `history:N | Tab 补全 | Esc 关闭`（ShellTerminalPanel.cpp 的
   `UpdateStatusText`）。HostOwned 下面板不再拥有这两个键，继续宣传
   它们就是**虚假广告**——用户看到提示去按键，没反应，报告"坏了"。

### 修复
提示语按 `FlowKeyMode` **自省**：只宣传终端实际拥有的键。
```
TerminalOwned → "history:N | Tab 补全 | Esc 关闭"
HostOwned     → "history:N"
```
宿主侧给 `HandleEscapeUI` 补注释，把"菜单场景空操作是有意的"写成
显式契约（含扩展指引：要给登录页 ESC 加语义就在此分支）。

### 原则
**UI 上的每一条按键提示都是与用户的契约，必须随键所有权自动一致。**
提示语硬编码 = 键所有权演进时必然产生"伪 bug"（行为正确但用户被误导）。
同类隐患排查方向：任何列出快捷键的 UI 文案（按钮 tooltip、帮助面板、
脚注）都应从键位数据源生成，而非手写。

## 6. 沉淀的架构原则（防同类问题）

1. **键归属矩阵**（契约，写入《宿主接入指南》§6.6）：
   - 文本编辑键（字符/方向/回车/Home/End/**Ctrl+C**）→ 终端面板；
   - 流控键（Tab/ESC）→ **宿主范式决定**（`FlowKeyMode` 声明式配置）；
   - 指针（点击/滚轮）→ 悬停命中的那块屏；
   - 游戏键（WASD/空格/视角）→ 角色（UI 输入接管态让位）。
2. **命令层只广播状态，表面层订阅呈现**——输出与 prompt 同款模式；
   命令代码出现 `CreateWidget/AddToViewport/SetInputMode` 即越权。
3. **输入模式/光标策略唯一所有权**：全部经 PC 的 `SetShellUIFocus`
   （GameAndUI + `SetHideCursorDuringCapture(false)` ↔ GameOnly）。
4. **自包含组件**：`UShellWorldScreen::SetInputActive(true)` 一个开关
   涵盖输入绑定、多屏仲裁、焦点断言；调用方无需理解内部机制。
5. **语义与监听分离**：监听放在焦点必经层，语义经委托归还所有者
   （`OnHostFlowKey` 模式，可复制到任何"嵌入宿主的面板"场景）。
6. **幂等 + 帧重试**：运行时构建的输入资产惰性创建；PC 未就绪按帧
   重试并封顶告警，杜绝静默死区。
7. **诊断常态化**：hover 探针、注入式键路由定位、运行时 IMC 读取
   （`get_applied_imcs`）——输入问题不猜，插桩拿数据。

## 7. 工程流程坑（与代码无关，同样致命）

| 坑 | 症状 | 处置 |
| --- | --- | --- |
| 热重载命名 DLL | 修复"构建成功"但不生效 | 见 §3；每次核对 canonical DLL 时间戳 |
| Live Coding × PIE | PIE 运行中热补丁 PC 类 → 编辑器崩溃（StaticShutdownAfterError） | **绝不在 PIE 运行时 Live Coding**；停机全量构建 |
| 跨项目 UBT 互斥 | 构建报 "Unable to build while Live Coding is active" | 全局互斥锁按引擎 exe 路径命名，跨项目误伤；临时 `bAllowHotReloadFromIDE=false`（构建后还原） |
| Build.cs 相对路径 | `PublicIncludePaths` 相对 `Source/` 解析 | 用 `ModuleDirectory + "/子目录"` 拼绝对路径 |
| BuildConfiguration XML 节点 | 设置写了不生效 + schema 警告 | `bAllowHotReloadFromIDE` 属 `UEBuildConfiguration` 节点，非 `BuildConfiguration` |
| MCP 多编辑器会话 | 命令路由到错误的编辑器 | `list_editors`/`use_editor`/`drop_editor` 显式管理；写操作必须显式目标 |

### 验证工具箱（本文用到的可复用手法）
- **hover 探针**：`GetHoveredWidgetComponent()`（World 源 + 探针摆位）；
- **端到端动作**：`invoke_object_function` 直调 UFUNCTION
  （`PrintToTerminal` 批量灌行 + 截图 diff 验证滚动）；
- **键路由定位**：临时 `ProcessKeyDownEvent` 注入 + 焦点类型打印 +
  分层日志（面板透传/动作触发）；
- **运行时输入状态**：`get_applied_imcs` 读各玩家映射上下文注册与优先级；
- **视觉回归**：截图逐像素 diff（纯 Python PNG 解码，无需第三方库）。

## 9. 坑七：PIE 失焦→回焦后打字失灵（2026-09-08 补录）

> "输入焦点丢失"的回访：坑二的修复只覆盖了"点击落屏"一条路径，
> 但 PIE 内**点一下编辑器面板（日志/内容浏览器）再点回游戏视口**——
> `bShouldFlushPressedKeysOnViewportFocusLost=True`（DefaultInput.ini）flush 按键，
> 视口回焦后 Slate 键盘焦点落在 SViewport，不会自动回到终端输入框。
> 两场景（菜单登录屏 / 手持屏）都复现，且日志零告警（Slate 行为不打日志）。

**修复（三条互补路径，全部落在"焦点必然经过的层"）**：

1. **回焦断言**：新增 `UShellViewportClient`（`Shell/WorldScreen/ShellViewportClient.h`），
   把 `FViewportClient::LostFocus/ReceivedFocus` 转发为
   `UShellSubsystem::OnViewportFocusReceived` 广播（与输出/提示同款"命令层只广播状态"）；
   `UShellWorldScreen` 订阅后在 `IsInputActive() && 面片可见` 时 `FocusTerminal()`。
   门槛与 `SetInputActive` 同源 —— 手持 HeldInHand 态不归还，避免抢移动输入。
   启用：`DefaultEngine.ini` → `[/Script/Engine.Engine]` →
   `GameViewportClientClassName=/Script/Shell_UE.ShellViewportClient`。
2. **同步断言替代延迟断言**：`SetShellUIFocus(true)` 与
   `AShellWorldScreenActor::ShowLoginScreen` 的 `FInputModeGameAndUI` 均显式
   `SetWidgetToFocus(Terminal->GetFocusTarget())` —— 不再把 `FocusTerminal()`
   的下一帧定时器当唯一保障（同帧内再次切换输入模式会吞掉它）。
3. **M5 收尾**：`RebuildHotkeyMapping` 的 `BindActionValueLambda` 绑定挂在
   InputComponent 上、不随 IMC 移除而失效 —— 保存句柄并在重建时
   `RemoveBindingByHandle` 清理，杜绝每次广播累积死绑定。

**验证手法**：复现路径下打印 `FSlateApplication::Get().GetKeyboardFocusedWidget()->GetTypeAsString()`——修复前回焦后是 `SViewport`，修复后应为 `SEditableText`。

> 后续若再遇"按键被吞/输入模式漂移"，先查本文 §0 速查表与 §6 原则，
> 再用 §7 工具箱插桩定位——不要从特例 if/else 开始。

## 10. 坑八：悬浮按钮开菜单抢焦导致 WASD 失效（M6 修复，2026-09-09 补录）

### 现象
游戏处于 **HeldInHand 态**（手持面板，纯游玩输入）时按 **Alt**（M5 默认快捷菜单
开关键）唤出悬浮快捷菜单后，**WASD / 空格全部失效**——角色动不了。按 **Tab**
切到 InputWindow 呈现态再切回（或关掉菜单）后恢复。

### 真因
M5 的 `UShellFloatingQuickButton::ToggleMenu()` **无条件 `FocusTerminal()`**。
菜单开合的代码路径不去看当前表面的活跃度，直接把键盘焦点塞进终端输入框
`SEditableText`——`SEditableText` 一旦聚焦就**吞掉字母键**（WASD 变成"打字
内容"，到达不了角色移动输入）。而游戏 HeldInHand 态**根本不该存在打字面**
（输入接管 `SetInputActive(false)`），抢焦是纯粹的越权：这是"谁拥有键盘焦点"
的裁决散落在各调用点（坑二/坑七各自打补丁）留下的同类缺口，这次被
"开菜单"路径触发。

### 修复（M6：声明式输入状态）
焦点断言收口到 `UShellInputStateManager` 后，悬浮按钮不再自己聚焦：

1. `ToggleMenu` / `OpenMenu` / `CloseMenu` 改为调 `UpdateInputStateForMenu(IsOpen)`
   ——按菜单开合状态翻译成输入状态，**不再无条件 `FocusTerminal()`**；
2. **菜单开** → 有活动打字面（`IsInputActive()` + 面片可见）→ `UiTyping`
   （继续打字要焦点）；否则 → `UiBrowse`（`GameAndUI` 但**不抢键盘焦点**，
   WASD 保留给游戏）；菜单关且本次切到过 `UiBrowse` → 回落 `Gameplay`；
3. **不变式兜底**：`Shell::InputState::ShouldStealKeyboardFocus` 只在
   `Focus == TerminalText` **且**存在活动打字面时才放行 `SetKeyboardFocus`；
   全插件唯一的 raw `SetKeyboardFocus` 在管理器 `ApplyFocusForState()` 一处。
   即使未来某处再写"开 UI 就聚焦"，只要当时没有活动打字面，焦点也抢不走。

### 验证手法
HeldInHand 态按 Alt 开悬浮菜单 → 打印
`FSlateApplication::Get().GetKeyboardFocusedWidget()->GetTypeAsString()`：
修复前是 `SEditableText`（WASD 被吃），修复后应无 UI 焦点（WASD 可移动）。
InputWindow 态开菜单 → 焦点应正常进终端（打字可用，属预期内抢焦）。

### 关联
与坑二（Slate 焦点 per-user）、坑七（PIE 回焦打字失灵）同属"焦点断言集中化"
脉络：M6 把"什么情况下允许抢键盘焦点"从各表面的临时判断收口为一个不变式，
悬浮按钮抢焦是这个缺口最后一次以"开菜单"为入口的暴露。
